# RESTOR-PC Boot Manager v1.2.0

## Overview

v1.2.0 ne change pas l'architecture de boot validée en v1.1.0. Aucune entrée de menu n'est ajoutée. Le thème, `config/refind.conf` et `win_vesty.png` restent ceux de v1.1.0.

Cette version est une release de durcissement et de validation. Elle ajoute une chaîne à trois niveaux :

1. **Niveau 1 — analyse statique et sûreté du dépôt.** Syntaxe PowerShell, PSScriptAnalyzer, contrôles de scripts et absence de portes dérobées dans le laboratoire.
2. **Niveau 2 — Pester offline.** Fixtures synthétiques et mocks. Aucun disque n'est ouvert.
3. **Niveau 3 — restauration réelle sur VHDX isolé.** `Restore-RestorBootManager.ps1` est lancé avec `-Apply` et `-ConfirmRestore "RESTOR-PC"` contre un disque virtuel, jamais contre le NVMe physique.

Les niveaux 2 et 3 n'utilisent pas le vrai NVMe.

Le tag `v1.1.0` reste sur `1dcfffa98dd0b1ce27c0b56a27c7be47f0df81a6`. v1.2.0 ne le déplace pas.

## What's new

### CI and repository validation

GitHub Actions exécute **RESTOR-PC CI** (`.github/workflows/ci.yml`) sur `windows-latest`. Le job s'appelle `Repository validation`. C'est le check requis pour protéger `main`.

`actions/checkout` est en `v7`. Les permissions du workflow sont `contents: read`. La concurrence annule l'exécution précédente de la même ref. Le timeout est de 15 minutes.

La commande locale équivalente est :

```powershell
pwsh -NoProfile -File .\scripts\Test-Repository.ps1
```

### PowerShell quality gates

`config/PSScriptAnalyzerSettings.psd1` n'exclut aucune règle. Les erreurs sont bloquantes. Trois warnings sont aussi des portes de non-régression : catch vide, affectation d'une variable automatique, paramètre inutilisé.

Les warnings restants sont des choix documentés, pas une liste de défauts ouverts :

- `PSAvoidUsingWriteHost` : les lignes `[OK]`, `[WARN]` et `[ERROR]` passent par `Write-Host`.
- `PSUseSingularNouns` : les noms de fonctions existants ne sont pas renommés.
- `PSUseShouldProcessForStateChangingFunctions` : `ShouldProcess` est posé seulement avant certaines écritures réelles. Les retraits de lettres dans un `finally` et les constructeurs du banc QEMU ne demandent pas de confirmation interactive.

Pester `5.9.1` et PSScriptAnalyzer `1.25.0` sont figés dans `config/ToolVersions.psd1`. La CI les installe avec `-RequiredVersion`.

### Offline behavioral tests

`scripts/Test-Behavior.ps1` lance Pester 5.9.1. `scripts/Test-Repository.ps1` l'appelle, donc un échec Pester fait échouer `Repository validation`.

Les tests couvrent notamment un Golden Backup corrompu, le dry-run, `-Apply` sans confirmation, une confirmation inexacte, l'identité disque, les codes `robocopy` et le refus d'un `-PreRestoreRoot` dangereux. Le matériel est simulé. La phrase de garde des mocks est `REAL HARDWARE ACCESS BLOCKED BY TEST`.

### Synthetic Golden Backup tests

Les fixtures sont construites dans le dépôt de test. Elles ne contiennent pas le Golden Backup réel, pas de `boot.wim` de production, pas d'image QEMU et pas de `Lockpick.iso`.

Le hash attendu de `win_vesty.png` reste `CC67BBF03D668EE61DE3A4F620C3855DF4D2430F2D2BCB473658CF1CE53331F6`.

### Restore safety

Sans `-Apply` et sans la confirmation exacte, `Restore-RestorBootManager.ps1` s'arrête avant toute copie. La comparaison est `-ceq` : `RESTOR-PC` est accepté, `restor-pc` ne l'est pas.

`-PreRestoreRoot` choisit le parent du dossier `PRE-RESTORE-...`. Le défaut production reste `C:\RESTOR-PC-BACKUP`. Un chemin vide, une racine de lecteur, `Windows` ou `System32` sont refusés.

L'ordre d'écriture est : contrôle du backup, identité du disque, correspondance des partitions, copie PRE-RESTORE, puis copie Golden. Un échec du pré-backup arrête la restauration avant la copie Golden. `robocopy` utilise `/E`, pas `/MIR` : un fichier absent du manifeste est conservé.

`Restore-RestorBootManager.ps1` recalcule le SHA256 du fichier `Manifests\SHA256-MANIFEST.txt` et le compare à `ManifestSha256`. Avec `-Apply`, un `Status` autre que `VALID` est refusé. Le script ne recalcule pas le hash de chaque fichier listé avant la copie. Un fichier remplacé après la sauvegarde, alors que le manifeste et `BACKUP-INFO.json` restent cohérents entre eux, peut donc être écrit. `Test-RestorGoldenBackup.ps1` recalcule chaque empreinte. Il doit réussir avant un `-Apply`.

Le script de production ne reconstruit pas le GPT. Il n'appelle pas `Clear-Disk`, `Initialize-Disk`, `Remove-Partition`, `Resize-Partition`, `New-Partition`, `Format-Volume`, `diskpart clean`, `bcdboot` ni `bootrec`.

### Isolated VHDX restore lab

`scripts/Test-VirtualRestore.ps1` demande PowerShell 7 et une session administrateur. Il crée un VHDX dynamique d'environ 4 Gio sous `test\vhd\restore-lab\`.

Le backend utilisé pour la preuve locale est `New-VHD`. Si `New-VHD` est absent, le script peut retomber sur `qemu-img.exe create -f vhdx`. Il n'active aucune fonctionnalité Windows et n'ouvre pas `\\.\PhysicalDrive`.

Le disque du laboratoire est toujours celui renvoyé par :

```powershell
Get-DiskImage -ImagePath <chemin-vhdx> | Get-Disk
```

`Assert-RestorVirtualLabDisk` exige que ce disque existe, soit attaché, porte le même numéro, ait `IsBoot=false` et `IsSystem=false`. Le modèle `SAMSUNG MZVLB256HAHQ-000L2` lève `PHYSICAL RESTOR-PC NVME BLOCKED`.

Cinq partitions GPT EFI FAT32 sont créées, type `{c12a7328-f81f-11d2-ba4b-00a0c93ec93b}` :

| Volume | Libellé FAT | Taille demandée |
| --- | --- | --- |
| RESTOR-BOOT | RESTOR-BOOT | environ 900 Mio |
| CODE-EFI | CODE-EFI | environ 500 Mio |
| VESTY-EFI | VESTY-EFI | environ 500 Mio |
| RESCUE-EFI | RESCUE-EFI | environ 500 Mio |
| LOCKPICK-EFI | LOCKPICK-EF | environ 900 Mio |

Le numéro de disque Windows observé pendant un essai n'est pas une constante du produit.

Le test lance le script de production avec `-Apply` et `-ConfirmRestore "RESTOR-PC"`, en redirigeant `-PreRestoreRoot` dans le laboratoire. Le Golden Backup utilisé est synthétique. Les lettres ne sont pas supposées être R, S, T, W ou Z.

`Dismount-DiskImage` s'exécute dans un `finally`. La suppression du dossier n'est permise que si le chemin résolu est exactement `<repo>\test\vhd\restore-lab`. `-KeepLab` démonte le VHDX et garde les fichiers. Un échec démonte aussi le VHDX et garde le laboratoire.

Ces tests portent le tag `VHD`. `Test-Behavior.ps1` les exclut. GitHub Actions ne les exécute pas. `scripts/Test-VirtualLabSafety.ps1`, lui, est statique et fait partie de `Test-Repository.ps1`.

### KeepExisting

`-KeepExisting` sur `New-RestorVirtualLab.ps1` réutilise un laboratoire déjà initialisé.

- VHDX absent : le fichier est créé, puis le GPT et les cinq partitions sont créés.
- VHDX présent, disque RAW ou sans partition : après `Assert-RestorVirtualLabDisk`, le layout est initialisé.
- VHDX présent avec les cinq volumes valides : le script inventorie les partitions. Il n'appelle pas `Initialize-Disk`, `New-Partition` ni `Format-Volume`. Les données restent. Une lettre absente peut être ajoutée avec `Add-PartitionAccessPath`, seulement après l'assertion, sans reformatage.
- VHDX présent avec un layout incomplet ou invalide : le script s'arrête. Il n'ajoute pas de partition et ne reformate rien. Le message est `Existing VHDX layout is invalid; recreate the lab without -KeepExisting.`

Sans `-KeepExisting`, un VHDX déjà présent est démonté puis remplacé.

## Restore model

La commande de production sans écriture reste :

```powershell
.\scripts\Restore-RestorBootManager.ps1 `
  -BackupPath "C:\RESTOR-PC-BACKUP\v1.1.0-GOLDEN-..." `
  -RestorBoot
```

> [!CAUTION]
> La commande suivante écrit sur la partition cible. Elle ne sert pas à valider v1.2.0 sur le NVMe physique. Cette validation a été faite sur le VHDX isolé.

```powershell
.\scripts\Restore-RestorBootManager.ps1 `
  -BackupPath "C:\RESTOR-PC-BACKUP\v1.1.0-GOLDEN-..." `
  -RestorBoot `
  -Apply `
  -ConfirmRestore "RESTOR-PC"
```

## Safety guarantees

- Dry-run par défaut.
- `-Apply` seul est insuffisant.
- La confirmation exacte `RESTOR-PC` est obligatoire.
- `Test-RestorGoldenBackup.ps1` refuse un Golden Backup dont un fichier ne correspond plus au manifeste.
- `Restore-RestorBootManager.ps1` refuse un backup incomplet, un `ManifestSha256` différent du fichier manifeste, et, avec `-Apply`, un `Status` autre que `VALID`.
- La restauration ne rehash pas chaque fichier. Ce contrôle reste `Test-RestorGoldenBackup.ps1`, avant `-Apply`.
- Le laboratoire identifie le disque par le chemin du VHDX avant toute opération destructive.
- `IsBoot` et `IsSystem` sont refusés dans le lab.
- Le modèle NVMe physique est refusé dans le lab.
- Les tests de niveau 2 et 3 n'ouvrent pas ce NVMe.
- Les tests VHD ne tournent pas dans GitHub Actions.
- Aucune reconstruction GPT de production n'est automatique.

## Backup compatibility

v1.2.0 reste compatible avec le Golden Backup valide créé sous v1.1.0. Les conditions sont un `BACKUP-INFO.json` au statut `VALID`, un `ManifestSha256` égal au hash du fichier manifeste, des fichiers conformes à leurs empreintes et la structure requise. La conformité fichier par fichier est établie par `Test-RestorGoldenBackup.ps1`, pas par la copie de `Restore-RestorBootManager.ps1`.

`$BackupVersion` dans `Backup-RestorBootManager.ps1` reste `1.1.0`. Le dossier local `C:\RESTOR-PC-BACKUP\v1.1.0-GOLDEN-...` n'est pas renommé. v1.2.0 ne fabrique pas un nouveau Golden Backup réel.

Le Golden Backup v1.1.0 vérifié localement, et non publié, reste : 807 fichiers, 1 652 615 023 octets, manifeste `32C40191C6DD1EB9AB2333E5657389F0FEEDBED35DFDD05867D51F08D378E043`.

Si une partition EFI a disparu, la restauration des fichiers est toujours refusée. Le GPT se reconstruit à la main. v1.2.0 ne le fait pas à la place de l'opérateur.

## VHD restore proof

La preuve locale du niveau 3, avec le backend `New-VHD`, a montré :

- un VHDX isolé, cinq partitions FAT32 `RESTOR-BOOT`, `CODE-EFI`, `VESTY-EFI`, `RESCUE-EFI`, `LOCKPICK-EF` ;
- le script de production lancé avec `-Apply` et `-ConfirmRestore "RESTOR-PC"` ;
- un dossier PRE-RESTORE créé avant la copie Golden ;
- l'ancien contenu de la cible sauvegardé ;
- les fichiers du Golden synthétique restaurés ;
- 7 fichiers contrôlés par SHA256 ;
- 0 écart de hash ;
- 5 fichiers supplémentaires conservés, parce que la copie n'est pas un miroir ;
- `RESTORE-REPORT.json` au statut `VALID`.

Le numéro de disque vu pendant cet essai n'est pas documenté comme valeur fixe.

## Known limitations

- La couverture de 62.7 % est une mesure de cette release, pas un contrat.
- Les warnings PSScriptAnalyzer restants sont visibles et ne sont pas masqués. Ils ne sont pas traités comme des erreurs de CI.
- GitHub Actions ne monte pas le VHDX. La preuve `-Apply` reste locale et administrateur.
- QEMU continue de vérifier le menu. Il ne démarre pas les Windows complets.
- La reconstruction GPT d'un NVMe de remplacement reste manuelle.
- Le laboratoire VHDX ne contient pas `RESTOR-TOOLS`. Il couvre les cinq volumes EFI du restore de fichiers, pas le disque de production complet.
- `Restore-RestorBootManager.ps1` ne rehash pas chaque fichier du Golden Backup. `Test-RestorGoldenBackup.ps1` le fait et doit précéder un `-Apply`.
